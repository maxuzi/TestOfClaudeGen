# Project: TestOfClaudeGen

Inherits all global rules from d:\WORK\CLAUDE.md.

## What this project is
- A training solution for generating X.Proto-based solutions from a draw.io UML.
- The single source of structure is `UML.html` in this folder (a copy of the one in X.Proto_ML_Skills). Classes are changed only through the UML.

## Project-specific rules
- Generate strictly from `UML.html` + `X.Proto.Framework.v5\!docs\X.Proto_ML_Skills`. Do not look at TutorialDemoProject.
- Do not list the skills folder recursively (it would expose the tutorial file names); list only `StageApplications` and `StageEndpoints`.
- Looking into TutorialDemoProject: originally restricted to one file at a time via a skills doc's **"go to xxx.cs"** reference. Mak lifted that on 2026-09-20 ("refresh in mind the TutorialDemoProject based on templates there") — browsing the tutorial broadly to refresh which templates exist is now fine. What still never changes: reproduce only *structural pattern* from the tutorial — base class, overridden method signatures, namespace/folder convention, registration idiom. Never copy a field, constructor dependency, or other business content that the current UML page does not itself show. If the UML is silent, the generated class stays silent too (parameterless stub), even if the tutorial has more — that gap is itself useful feedback for Mak, not something to paper over. (Exception: a base class's own constructor parameters, read from the framework source, are a compile-time necessity once you extend that class, not a content choice — those are fine regardless of what the UML shows.) UML is always the source of *content*; the tutorial is only ever a source of *pattern*.
- The framework source itself (X.Proto.* projects, MigrationsDb.pg_000_sys) may be read to resolve APIs and constructor parameters.
- `UML.html` is a draw.io HTML export: decode the `data-mxgraph` attribute (HtmlDecode -> JSON -> `xml`) with PowerShell. Pages: `UseCases` (id UC) + one class page per use case. Stereotypes: «XPK» primary key, `<<INCLUDE>>` include into PK, «XUK» unique, «table» / «table-cmps» / «table-aggr». A use-case `<<include>>` edge = sub-folder inside the parent project, not a new project.
- Solution folders (virtual): Applications { Core, Endpoints, MigrationsDb, ReferenceEntities }, Debug, iOutsideApplications, LIB { X.Proto }.
- On disk all projects live flat in the solution root: `D:\WORK\TestOfClaudeGen\<ProjectName>\`.
- AssemblyName / RootNamespace of an application project = `TestOfClaudeGen.<UseCaseName>`.
- Framework projects are referenced by relative path `..\..\X.Proto.Framework.v5\<Project>\<Project>.csproj` and grouped under LIB\X.Proto.
- Git: `feature/claude` in X.Proto.Framework.v5 is the "claude" branch; never commit or push there. TestOfClaudeGen IS a git repo with a GitHub remote (`github.com/maxuzi/TestOfClaudeGen`) — do not commit or push here either unless explicitly asked.
- Mak maintains the «table» links in UML and renames .sql scripts himself; treat renamed files as new names.
- After every generation pass: `dotnet build TestOfClaudeGen.sln` must be clean, then report which gaps in the skills docs were filled from the framework (that feedback is the point of the experiment).

## Modules / microservices
- **Core.User** (use case UC01 → Crud template): `IUser : IXCrudComponent`, `User : XCrudComponent`, Autofac module `RUser` registers `Named<IXConnector>("IUser")` on table `usr.user`.
- **Core.User.Jobs** (use case → MasterDetails template): `IUserJobs : IXMasterDetail`, `UserJobs : XMasterDetail` (5-param ctor: composite + aggregate tables), Autofac module `RUserJobs` registers `Named<IXConnector>("IUserJobs")` with `pFieldComposit="jobs"`, `pTableComposit="usr.user_jobs_cmps"`, `pTableAgregate="usr.user_jobs_aggr"`.
  - **Posts** folder = the `<<include>>`d use case Core.User.Job.Posts: `IUserJobPosts : IXMasterDetail`, `UserJobPosts : XMasterDetail` (4-param ctor: composite only), registered in the same `RUserJobs` as `Named<IXConnector>("IUserJobPosts")` on `usr.user_job_posts_cmps`.
- **Core.BT.Calc** (use case, reached from actor "Calculator" → direct-IXConnector + ChainResponsibility templates): `ICalc : IXConnector`, `Calc : ICalc` (field `_chainProcess: IXChainResponsibility`, `Calculating` stubbed as `NotImplementedException`). `ChainLinks/` folder: `BT_CountryBase` (abstract : `XChainFlowBase`, protected `multiplexor: IXMultiplexor`), `BT_DocumentsLink` (: `XChainFlowBase`, field `_invoker: IXInvoker`), `BT_ForbidLink`, `BT_BonusLink` (both : `BT_CountryBase`). `HandleLink`'s parameter is `pParamChainData` everywhere (the UML/docs are explicit that this name must match exactly). `RCalc` registers `Calc` as `Named<IXConnector>("ICalc")` and each chain link as `Named<XChainFlowBase>("<ClassName>")` — the registration key is the C# class name, not UML stereotype text (confirmed via the tutorial's `RCalc.cs`; the current UML now just uses a generic `<<named>>` marker with no abbreviation, consistent with this).
  - `ChainLinks/BON_Plexes/`: `BT_BON_InsertInfo`, `BT_BON_InsertDetail` (both : `XTaskPlexBase`, driven by `BT_BonusLink`'s own detail page). Both stubbed, registered `Named<XTaskPlexBase>("<ClassName>")`.
  - `ChainLinks/FRB_Plexes/`: `BT_FRB_SelectCountryPlex` (no fields, stub), `BT_FRB_SelectEmployeePlex` (field `_invoker: IXInvoker` — Mak added this to the UML on 2026-09-20 after I'd wrongly copied it from the tutorial in an earlier pass; it's now legitimate UML content). Both override `RunFunc` (the UML page mislabels the abstract's method as `RunTask(...): Task`, copied from the `XTaskPlexBase` page — the real framework contract for `XFuncPlexBase` is `RunFunc(XData): Task<XData>`, used instead). Registered `Named<XFuncPlexBase>("<ClassName>")`.
  - **Employee_Country** folder = the Core.BT.Calc.Employee_Country use case (ManyToMany template): `IEmployee_Country : IXManyToManyComponent`, `Employee_Country : XManyToManyComponent`, namespace `...Core.BT.Calc.EmployeeCountry` (no underscore — matching the class name verbatim would collide with the type; the tutorial dodges this with a pluralized namespace, we use a cleaner non-colliding one instead). Registered in the same `RCalc` as `Named<IXConnector>("IEmployee_Country")` on `clc.employee__country`. The UseCases page now has an explicit `<<include>>` label on the Core.BT.Calc → Employee_Country edge, confirming the subfolder placement (was ambiguous in the previous UML revision).
- **MigrationsDb.pg_001_usr** (DbUp, postgres): schema `usr`; `001_usr_CT_user.sql` → `usr.user` (`XPK_user` on id INCLUDE name, `XUK_account`); `0040_usr_CT_user_jobs.sql` → `usr.user_jobs_cmps` + `usr.user_jobs_aggr`; `0060_usr_CT_user_job_post.sql` → `usr.user_job_posts_cmps`. After first generation the .sql files are primary, the UML «table» elements are secondary.
- **MigrationsDb.pg_002_clc** (DbUp, postgres, new schema `clc` per 01_DbObjectsRules.txt "new scheme" rule): `0000_clc_schema.sql`, `0020_clc_CT_Employee_Country.sql` → `clc.employee__country` (employee_id, country_id, `rules JSONB`; mirror unique constraints `XUKm1_employee_country` / `XUKm2_country_employee` per the `<<XUKm1>>`/`<<XUKm2>>` stereotypes).
- **MigrationsDb.pg_000_sys**: framework system-schema migrations, linked from X.Proto.Framework.v5.
