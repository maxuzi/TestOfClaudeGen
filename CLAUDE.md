# Project: TestOfClaudeGen

Inherits all global rules from d:\WORK\CLAUDE.md.

## What this project is
- A training solution for generating X.Proto-based solutions from a draw.io UML.
- The single source of structure is `UML.html` in this folder (a copy of the one in X.Proto_ML_Skills). Classes are changed only through the UML.
- root.md (2026-09-23) now names three stages/commands, each its own phase of work:
  - **"use apps stage"** → StageApplications (business logic, what all passes so far have done).
  - **"use endpoints stage"** → StageEndpoints (ASP.NET Core web apps: Endpoint / outside.WebApp / outside.App — see below).
  - **"use endpoints-apps-relations stage"** → StageEndpointsAppsRelations (wiring Endpoint↔Endpoint calls via XInvoker; not documented yet).

## Project-specific rules
- **Field access-modifier legend (Mak's, 2026-09-23 — note this inverts standard UML!): `+` = protected, `-` = private.** Also: generate the field name exactly as the UML label spells it, including any leading underscore — the label itself decides whether the C# name gets one (e.g. `- _invoker: IXInvoker` → `private ... _invoker`; `+ multiplexor: IXMultiplexor` → `protected ... multiplexor`, no underscore because the label has none). Audited every previously-generated field against this on 2026-09-23 and all matched except `UserFacade`'s (see Core.User.Facade below and History) — so apply it, but a full re-audit isn't needed every pass, just to new/changed fields.
- Generate strictly from `UML.html` + `X.Proto.Framework.v5\!docs\X.Proto_ML_Skills`. Do not look at TutorialDemoProject.
- Do not list the skills folder recursively (it would expose the tutorial file names); list only `StageApplications` and `StageEndpoints`.
- Looking into TutorialDemoProject: originally restricted to one file at a time via a skills doc's **"go to xxx.cs"** reference. Mak lifted that on 2026-09-20 ("refresh in mind the TutorialDemoProject based on templates there") — browsing the tutorial broadly to refresh which templates exist is now fine. What still never changes: reproduce only *structural pattern* from the tutorial — base class, overridden method signatures, namespace/folder convention, registration idiom. Never copy a field, constructor dependency, or other business content that the current UML page does not itself show. If the UML is silent, the generated class stays silent too (parameterless stub), even if the tutorial has more — that gap is itself useful feedback for Mak, not something to paper over. (Exception: a base class's own constructor parameters, read from the framework source, are a compile-time necessity once you extend that class, not a content choice — those are fine regardless of what the UML shows.) UML is always the source of *content*; the tutorial is only ever a source of *pattern*.
- The framework source itself (X.Proto.* projects, MigrationsDb.pg_000_sys) may be read to resolve APIs and constructor parameters.
- `UML.html` is a draw.io HTML export: decode the `data-mxgraph` attribute (HtmlDecode -> JSON -> `xml`) with PowerShell. Pages: `UseCases` (id UC) + one class page per use case. Stereotypes: «XPK» primary key, `<<INCLUDE>>` include into PK, «XUK» unique, «table» / «table-cmps» / «table-aggr». A use-case `<<include>>` edge = sub-folder inside the parent project, not a new project.
- Solution folders (virtual): Applications { Core, Endpoints, MigrationsDb, ReferenceEntities }, Debug, iOutsideApplications, LIB { X.Proto }.
- On disk all projects live flat in the solution root: `D:\WORK\TestOfClaudeGen\<ProjectName>\`.
- AssemblyName / RootNamespace of an application project = `TestOfClaudeGen.<UseCaseName>`.
- Framework projects are referenced by relative path `..\..\X.Proto.Framework.v5\<Project>\<Project>.csproj` and grouped under LIB\X.Proto.
- Git: `feature/claude` in X.Proto.Framework.v5 is the "claude" branch; never commit or push there. TestOfClaudeGen IS a git repo with a GitHub remote (`github.com/maxuzi/TestOfClaudeGen`) — do not commit or push here either unless explicitly asked.
- Mak maintains the «table» links in UML and renames .sql scripts himself; treat renamed files as new names.
- After every generation pass: `dotnet build TestOfClaudeGen.sln` must be clean, then report which gaps in the skills docs were filled from the framework (that feedback is the point of the experiment).

## StageEndpoints
Source is a UML page type `DC` (Deployment Chart): custom XML attributes on each node (`Type`, `ConnectionString`, `Route`, `IsSwagger`, ...), not visible cell text — read these with `.object.Type` / `.object.ConnectionString` etc., not the value/label dump. `SolutionName` is a custom attribute on the page's own root object (id `0`). Grouping (which Core.* apps / Controllers belong to which module) is **purely visual** — child shapes sit geometrically inside the parent's `shape=module` bounding box, no XML parent/child link (`container=0` on every cell) — so containment must be computed from `mxGeometry` x/y/width/height, not from `parent=`.

- **Endpoint** type → `.NET Core Empty`/`Sdk.Web` project in `Applications/Endpoints`. AssemblyName/RootNamespace = `SolutionName.<DC ID>`. References: the framework infra its included Core.* apps actually need (tutorial's example needed `Endpoints.Invoker.RabbitMQ`, `Endpoints.Setup.Autofac`, `Endpoints.Setup.ConfigFiles`, `Common.Events`) plus a `ProjectReference` to every grouped Core.* project — "must include all possible references for running", i.e. this is the actual host process. `CONFIGS/appconfig.json`: a `PoolConnections` array (`ConnectionType`+`ConnectionString`) only if the DC node's `ConnectionString` property is non-empty. `CONFIGS/autofac.json`: a `modules` array — `RXServiceConnector`, `RXEvents`, `RXDbApi`, `RXDbPostgreSQL` if any grouped app touches a DB, one `RX<Template>` per component template actually used, then one `R<AppName>` module per grouped Core.* project. **No invoker registration in this file** even though the project references `Invoker.RabbitMQ` — confirmed against the tutorial's actual `autofac.json` content (not just its csproj): the reference exists but wiring it is StageEndpointsAppsRelations' job.
